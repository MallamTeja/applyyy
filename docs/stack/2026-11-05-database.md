Append-only and immutable tables get two triggers, `forbid_update` and `forbid_delete`, both
running `applyy_internal.forbid_mutation`. They cover `application_events`, `gemini_usage`,
`resume_chat_messages` and `master_profiles`. Their table grants also revoke writes, so the
triggers and the grants enforce the same rule twice.

Every new table needs a matching `Row` type in `packages/shared-types/src/tables.ts`; a parity
test compares types with migrations.

### Jobs tombstone (space policy)

Migration `20261105200000_jobs_tombstone.sql`. Old `dropped_filter` jobs keep their slim row
(id, fingerprint, company, title, URL, dates) but lose the heavy description and raw JSON.
The row is never deleted, because scouts dedupe on `(user_id, fingerprint)`: deleting it
would let the next scan re-insert a rejected job as new. `tombstone_dropped_jobs(p_min_age_days,
p_batch_size)` does the work; the trigger `jobs_keep_tombstone_slim` keeps a tombstoned row
slim. `jobs-tombstone.yml` runs it weekly and logs to `agent_runs` as `jobs_tombstone`.

## Triggers on `applications`

BEFORE INSERT `guard_status_insert` → BEFORE UPDATE `guard_status_transition` (SECURITY
DEFINER), `guard_tailored_profile_freeze`, `guard_failed_rerun`, `set_updated_at` → AFTER
UPDATE `log_status_change` (SECURITY DEFINER, writes `application_events`). Together these
make the status graph a database-enforced state machine. No client can skip an edge, even
one holding a valid JWT. Read the graph itself with
`select from_status, to_status, allowed_agents from application_status_transitions order by 1,2`
(53 edges as of 2026-11-08). New since 2026-11-05: a `human` edge from `approved` to
`applied` / `failed`, for jobs applied by hand from the Manual apply page
(`20261105121500_human_resolves_approved_from_manual_apply.sql`).

## Grants note

On 2026-11-05 `anon` and `authenticated` kept Supabase's default full DML grants (TRUNCATE
included) on most `public` tables. Migration `20261105203000_revoke_definer_execute_and_truncate.sql`
revokes TRUNCATE from both roles on every `public` table, and on future tables through
`alter default privileges`. RLS blocks every row operation for `anon`. Re-check with
`select grantee, table_name, privilege_type from information_schema.role_table_grants where table_schema = 'public' and grantee in ('anon','authenticated')`.
