# Ready-queue #2 — apply-run DB-timeout throw (2026-11-23 ~20:50 IST)

**Root cause:** a cold Supabase Storage → Postgres connection made the first upload of the run fail. It is not a PostgREST query and not a slow table.

Evidence:
- **Run log, `apply.yml` run 45160947946, 10:59:44 UTC:** `errors=1 … uploadScreenshot failed: The connection to the database timed out`.
- **edge_logs, 10:59:23.83 UTC:** `POST /storage/v1/object/screenshots/…/f4e2f35f…/1795431563811.png` answered **544** (Storage's own "database timeout"). storage_logs shows the same request.
- **pgbouncer, 10:59:28.73 → 10:59:30.04:** `supabase_storage_admin login attempt` → `new connection to server` → `SSL established` → `client unexpected eof (age=6s)`. Storage opened a fresh Postgres connection and its ~5 s connect timeout expired first.
- **Why cold:** the previous Storage write was 2026-11-22 10:02 UTC, about 25 h earlier.
- **Next upload succeeded:** 13 s later (10:59:36, row e83ee97f) it answered **200**.
- **The failed object never landed:** `storage.objects` has e83ee97f's 10:59:38 object, but nothing for f4e2f35f on 11-23 (it did on 11-22).
- **Frequency and size:** 1 applier run with a timeout out of 30 in 30 days. The buckets are tiny (50 screenshots, 228 resumes), so size is not the cause.

**Why it matters for a live run:**
- `unwrap` turned Storage's returned `{ error }` into a throw, and the claim loop's breaker trips on any throw (`claim-loop.ts:691-721`).
- In a live run, `uploadResume` is the FIRST Storage call (`apply-one.ts:890-891`), so the cold start hits the resume. The row is lost and the run stops: 0 submitted.

**Fix (`worker/src/supabase-gateway.ts`):**
- `uploadScreenshot` and `uploadResume` go through one `uploadArtifact`. It retries ONLY transient answers: a closed set {502, 503, 504, 544} read by shape from storage-js 2.7.1's `StorageApiError.status`, plus `StorageUnknownError` (network).
- Waits are 2 s, then 5 s (worst case +7 s on one row). `GatewayConfig.storageRetryDelaysMs` makes them injectable.
- Each attempt gets a fresh timestamped path, so a retry never collides with a half-landed object.
- Refusals (4xx) still throw on the first answer, with the same message shape as before.
- No index or migration needed: this is a Supabase-side cold start, not a query plan.

**Test (`worker/test/supabase-gateway.test.ts`, describe "artifact uploads: transient Storage answers are retried, refusals are not"):**
- 4 tests whose fakes RETURN `{ error: { name: 'StorageApiError', message: 'The connection to the database timed out', status: 544 } }`. They do not throw, matching supabase-js.
- Red before the fix: 3 failed (screenshot retry, resume retry, bounded retries; full-suite run at 20:32 showed `3 failed | 930 passed`). The 403 no-retry test passes on both sides by design.
- After the fix: 41/41 in the file.

# Ready-queue #2, round 2 (peer 4 = applyyy-7d, 2026-11-23 23:25 IST): the inherited fix did not retry the real answer

**Root cause (re-measured):** run 45160947946, job 137645938697, `10:59:44Z … errors=1 … continued after error: uploadScreenshot failed: The connection to the database timed out`. That is a Storage upload (`supabase-gateway.ts` `uploadScreenshot` → `client.storage.upload`), not a PostgREST query. The 544 status itself is not in the run log (`unwrap` kept only the message); it comes from edge_logs (round 1 above). 1 of 7 readable prior runs hit it; 3 prior run logs were unreadable (GitHub API timeouts).

**Bug in the round-1 fix:** storage-js 2.7.1 `upload()` does NOT return a `StorageApiError` on a non-2xx answer. It returns the server's raw JSON body as `error` (`StorageFileApi.js:85-87`): `{ statusCode: "544", error: "DatabaseTimeout", message }`, with the status as a STRING under `statusCode`. Round 1 read only a numeric `status` plus `name === 'StorageUnknownError'`, so the real 544 read as a refusal and still threw. Its test faked `{ name: 'StorageApiError', status: 544 }`, a shape `upload()` never returns (repo CLAUDE.md §5: a test double must behave like the real dependency). Also, with no JSON answer at all (network drop → fetch TypeError; HTML 502 → `res.json()` SyntaxError), `upload()` THROWS, and that throw escaped the retry loop.

**Fix (`worker/src/supabase-gateway.ts`):**
- `storageErrorStatus` reads the status by shape: an integer `status`, or `statusCode` as exactly three digits (or an integer). Anything else is null, and null is never transient.
- `uploadArtifact` wraps the `upload()` call in try/catch. A thrown no-answer is retried on the same 2 s / 5 s schedule; once the schedule is spent, the ORIGINAL error is rethrown, so a real bug still surfaces.

**Tests (`worker/test/supabase-gateway.test.ts`):** the fakes now return the real raw-body shape. +2 tests: "uploadResume retries when upload() throws with no JSON answer", and "a throw that persists past the schedule is rethrown unchanged".

**Red on revert (bytes restored, `cmp` identical after each):**
- Disable the `statusCode` read → 3 named tests red (the screenshot 544 retry, the resume 544 retry, bounded retries).
- Remove the catch-and-retry → 2 named tests red (the throw retry, rethrown unchanged).

**Gates:**
- Worker tsc: 0 errors.
- Worker vitest: 954 passed, 1 failed, 71 files. The one failure is `submit-outcome-real-form.test.ts` "browser-native required field empty", a 30 s Playwright timeout while 3 vitest runs were competing for CPU. Rerun alone: 1 passed. It does not touch the gateway.
