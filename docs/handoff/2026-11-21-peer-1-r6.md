## (1) Chat `set_role` obeys the Aczen title allow-list

- **The gap** (from peer 3's r3 bridge):
  - `setEntryRole` (`apps/web/src/features/approval/tailoredEdits.ts`) wrote any well-formed title onto any experience.
  - So "change aczen title to data analyst intern" printed the FamPay title, past the tailor's
    `EXPERIENCE_TITLE_ALLOW_LIST` (`supabase/functions/_shared/tailor/validator.ts:135`, committed e1f4b520).
- **The rule** (orch ruling): for an experience the list names (today only `exp_aczen`), the title must be one on the
  list. Every other experience keeps its dictated title (Teja 11-11).
- **How it is built:**
  - It reads the list by relative import, the same way the file already imports `ROLE_TITLE_SHAPE`. There is no copy.
  - It matches the entry's `ref`, which is the master id, against the list's keys.
  - The match ignores case and collapses spacing. What prints is always the list's own spelling, the exact form the
    validator compares.
  - An unlisted title is refused through the existing `EditOutcome` reason, which the page shows inline (no native
    dialog): "This job title must be one of: Full Stack AI Engineer Intern, Software Engineer Intern, Backend Engineer
    Intern, AI Engineer Intern. Background checks compare it with HR records."
- **New tests** (`apps/web/test/tailoredEdits.test.ts`, `describe('setEntryRole …')`):
  - "refuses a title outside the allow-list on exp_aczen…"
  - "accepts an allow-listed title on exp_aczen, printed in the list spelling…"
- **Kept and unchanged:** the old test that sets "Data Analyst Intern" on `exp-acme`. It proves that experiences not on
  the list keep dictated titles.
- **Still open (server side, peer 3's area):**
  - The `resume-assist` `set_role` example and tests still dictate free titles.
  - The web now refuses an unlisted Aczen title at apply time, so the chat may *propose* one the page then refuses with
    the reason above.
  - Teaching the prompt to offer only listed titles for Aczen would avoid that round trip.
