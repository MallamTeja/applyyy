## Gap 1: a tech drop hid a work-auth drop

**Cause.** The regate used `auditorPreGateDrop`, which returns only `firstPreGateDrop`'s first code (tech, then work_auth, then experience). The sweep may act on work_auth only (the 11-11 rule). So a row failing tech AND work_auth was kept in Teja's queue, and a row failing tech AND experience was never reported.

**Fix, in `auditor/pregate.ts` (not `matcher/`, which is not my row):**
- New `auditorRegateGates(job, prefs)` → `{ workAuth, experience }`. It calls `screenWorkAuth` and `screenRequiredExperience` directly, with exactly the inputs `firstPreGateDrop` feeds them.
- It keeps the same refusals: a null job throws, and a pasted job passes.
- Tech is not asked, because the sweep never acts on it.
- The main `tailored` run is unchanged: there every code exits the same way, so the order does not matter.

## Gap 2: two queued copies of the same job both stayed

**Evidence before building:**
- The queue today has 26 awaiting rows, 21 with an ATS key, and **0 twin groups**. 0 rows would drop, well under the STOP limit of 2.
- In history, 2 ATS postings reached the approval queue twice. **One of them was applied to TWICE**: both copies are `applied`. The other pair is `dropped_filter`. So the rule has a real cost to prevent.

**Fix, in `auditor/regate-queue.ts`:**
- `queuedTwinOwners(rows)`: the oldest awaiting copy of each ATS key owns the posting. Age is ranked by `created_at`, then by id, so read order never decides.
- An unparseable stamp never owns a posting, so at least one copy always stays.
- A newer, non-pasted awaiting twin drops as `already_applied`. Its reason names the copy that stays.
- Rows that never drop as twins: the older copy, Teja's pasted copy, and an approved copy (W2 already covers committed rows).
- `QueueRow.created_at` is now required, and `auditor/index.ts` selects it.
- The regate read is cast to `QueueRow`, so the types cannot catch a missing column. A source-wiring test covers it instead.
