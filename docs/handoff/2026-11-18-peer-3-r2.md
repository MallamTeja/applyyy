## Design answers to the brief

- **Statuses matched:** all of `COMMITTED_STATUSES` plus `awaiting_approval`, checked against the live enum. `COMMITTED_STATUSES` is approved, applying, blocked_needs_human, needs_verification, applied, the four post-apply states, rejected, and failed *only when approved*.
- **Ruling conflict, flagged:** the brief said a prior `failed` row must NOT block. I applied that only to a **never-approved** `failed` row, which the adapter already filters out (`wasNeverApproved`). An **approved-then-failed** row (e.g. `human_did_not_submit`) still blocks. That matches the module's existing rule that it "may have been submitted, so fail CLOSED" for the fingerprint set. Making it not block means changing that rule for every set, not just mine. Your call; it is a one-line change in `context.ts`.
- **No merge:** rows are not merged. A retitle with no prior application is still screened, so the Keyloop Senior-to-Junior case survives.
- **Where it runs:** at screener insert only. Every new copy enters through `screen-batch` (scout-ats, the worker ATS scout, the remote scout, the screener). The auditor re-gate is not covered: it runs `firstPreGateDrop` (tech, work-auth, experience), which has no history. Adding history to the auditor means a new read in `auditor/` (outside my row). The census shows the only row it would catch today is 111d1ff4, which Teja is rejecting by hand. So screener-only is enough unless that recurs.
- **1000-row cap:** the history stays one page with an exact count. `checkComplete` refuses the run with a named `history_truncated` error, never a silent miss. The live total for committed plus awaiting rows is **188**, so the headroom is about 5×. The scout-remote "twin lookup truncated" is a different read in `worker/src/scout/remote-run.ts` and is not touched here.
- **Self-match:** none. Every applications insert is `ignoreDuplicates: true` on `(user_id, job_id)`, so a re-sighted job can never overwrite its own row.
