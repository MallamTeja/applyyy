## Contract check: prompt schema ↔ engine ↔ validator e1f4b520 — no mismatch

1. **Bullet `sources`:** the prompt schema requires them (`prompt.ts:630,655,680,708,735`).
   - `parseTailoredProfile` passes the model object through (`tailorer.ts:471-500`), and the rewrite merge spreads
     each bullet (`tailorer.ts:418`), so `sources` reaches `checkProvenance` (`validator.ts:446-503`).
   - Content-rule top-ups add master bullets without `sources` (`content-rules.ts:93`). Those take the verbatim path,
     which the validator still applies to source-less bullets.
2. **`role_title`:** the prompt enum is built from `EXPERIENCE_TITLE_ALLOW_LIST` (`prompt.ts:623`). The validator
   refuses only a present title outside the list (`validator.ts:778-782`); it does not require one. `toppedUp`
   spreads the entry, so `role_title` survives (`content-rules.ts:97`). An experience the content rules ADD
   (`content-rules.ts:172`) carries none and prints the master role: allowed, never refused.
3. **Skills:** the schema keeps skills as bare refs with no group field (`prompt.ts:601-607`), and the engine regroups
   by master category anyway. My engine ignores the model's grouping and drops never-list picks, reporting them.
   That is consistent: the prompt still lists never-list skills (`prompt.ts:222-227`), and dropping them costs a
   reported pick, not a refusal.
4. **Shared vocabulary:**
   - The prompt's `extracted_requirements` come from MY `extractJdKeywords` (`prompt.ts:20,763`), so the producer
     and the engine read one term list.
   - The validator's provenance check uses its OWN list (`PROVENANCE_TECH_TERMS`, `TECH_ALIASES`, master skill
     names; `validator.ts:146-181,290`). My vocabulary edits therefore neither loosen nor tighten provenance.
