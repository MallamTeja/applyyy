## Track 1: root cause and design

- **Not the 40-row cap.** In the last 12 `scout.yml` runs (11-20..11-23), `skipped` was 0 every run, with at most 20 detail reads. From 11-21, 56 to 64 of the 64 Workday boards were deferred on a robots.txt 429. That limit is S16's to fix; no HTTP client switch. The 85 thin rows were first seen 11-05..11-10. Since 11-18 a blank row is created at `passed_filters` with "No description" instead of being dropped (`screen-batch.ts:267-280`). The cap stays at 40.
- **The drain works.** Run 45334499027 did 30 rows in 10.5 min with no 429. The problem is that nothing triggers it: GitHub cron is best-effort.
- **Design:** GitHub-only triggers.
  - 3 cron slots per day.
  - A `workflow_run` after every scout run.
  - A self-redispatch chain (depth up to 8) that drains the whole backlog from any one trigger.
  - pg_cron/pg_net are ruled out (Teja 10-09). Page-load dispatch is ruled out (orch 12:55: a GitHub token would be a new credential surface).
  - Trade-off: a bulk SQL move waits for the next trigger, up to about 8 h.
- **Bug fixed in the inherited diff:** a carry of up to 200 ids plus 29 new tries could exceed `MAX_SKIP_IDS`, so the next run got HTTP 400 and ended red. The fix is `NEXT_LINK_ROWS = 30`, and the chain redispatches only while `carry.length + 30 <= 200`.
- **Known gap, accepted (bounded):** under concurrency `cancel-in-progress: false`, GitHub keeps one pending run per group. A cron firing while a chain run is pending replaces that pending run and drops its carry. The worst case is a depth-0 restart that re-tries known-thin rows.
- **Stale wording, parked files:** `scout-ats/index.ts:1294` has the same stale comment. The worker backfill in `persist-jobs.ts` re-reads the same oldest blank rows every run (20 fetched, 0 filled on 11-23). Both files are parked, so neither is touched.

## Track 2: behaviour

- **Ready lane:** `job:job_id!inner(...)` + `job.disappeared_at is null`, applied via the `laneRead(lane)` helper. The lane total is the counts RPC minus the gone count, and null when either read failed or gone > total. No migration.
- **"Gone after ready":** a collapsed `<details>` section, read with `count:'exact'`. Each row shows company, title, the `postingGoneNote` text, the Apply link and a one-click Reject. The reject is a new closed kind `reject_closed` that sends `reason`/`drop_reason` = `posting_closed`. Undo goes through the existing human edge.
- **Approvals:** `readQueue` is the only reader, now `jobs:job_id!inner` + `.is('jobs.disappeared_at', null)`. Rows already open keep `PostingGoneNotice` (no confirm on Approve, per the ruling).
- **Side effect of `!inner`:** a row whose job the user cannot read (an RLS mismatch) now leaves the list instead of showing "Job record missing". `job_id` is NOT NULL with a cascading FK, so only an RLS mismatch can do this.
- **Pipeline page counts:** they still include gone rows. They are raw per-status counts.
