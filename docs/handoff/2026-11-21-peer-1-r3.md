## 1. Bulk drop

- **How it works:**
  - Each Bucket A and Bucket B row gets a `Select` checkbox in its toolbar. The checkbox's accessible name is `Select <title> at <company> to drop`.
  - While any visible row is ticked, a bar appears above the buckets.
  - "Drop N selected" only arms the shared `InlineConfirm`. No native dialog is used; `inlineConfirm.test.ts` stays green.
  - Confirm calls the existing `settle(ids, 'dropped_filter', { drop_reason: 'bulk-dropped at approval gate' })`. That sends one `advance_application_status` RPC per row as `human`, 4 at a time.
  - Results come back through settle's per-outcome toasts: moved, failed, unconfirmed, settled elsewhere.
  - A row that fails stays on screen and stays ticked. So one failure hides nothing, and a retry is one click.
- **An unticked row is never sent.** `bulkDropTargets` builds the list from the **visible** rows: Bucket B minus `bucketBFilteredOut`, then Bucket A. Ticks only filter that list. A tick that outlives its row (searched away, or settled in another tab) cannot ride along. Approve all uses the same visibility rule.
- **The confirm is keyed on the target list** (`<InlineConfirm key={ids.join(' ')}>`).
  - Unticking a row while the confirm is open remounts the confirm, and InlineConfirm cancels its pending confirm on unmount (`InlineConfirm.tsx` unmount effect).
  - Without the key, Confirm would still drop the row that was just unticked. I caught that gap in my own first draft.
- **Not done:**
  - The failure toasts give counts, not job names. The failed rows stay visible and ticked instead.
  - Naming them would change the shared `settle` reporter, which every approve and reject path uses. I left it alone.
- **Styling:**
  - The bar's layout is inline, using spacing tokens (`var(--gap-3)`), because `ApprovalQueuePage.css` is not in my grant.
  - The checkbox reuses `button button--secondary` on its label.
  - If the orch wants it, I can move the layout into a class once the CSS file is granted.
