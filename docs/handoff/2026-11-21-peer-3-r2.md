## Fix 1: pause a key after 3 consecutive 429s

- **Where the pause lives: the database, shared by all instances.** There is no new table and no migration.
  - `pool.ts` `cooldownFor429(db, keyIndex, retryAfter)`:
    1. If the server gave a retry_after, it returns that value with no extra read.
    2. Otherwise it reads that key's existing `gemini_key_state.consecutive_failures`. If that count + 1 (this 429) is ≥ `RATE_LIMIT_PAUSE_AFTER` (3), it returns `RATE_LIMIT_PAUSE_SECONDS` (60).
    3. In every other case it returns null, which is the old behaviour.
  - It never throws. An unreadable or malformed streak returns null (shape-checked, §6).
  - `client.ts` passes that value to `reportResult` in the 429 branch. `claim_gemini_key` then skips the key for 60 s on every instance.
- **Why not in memory:** isolates are fresh per invocation, so a counter in memory would rarely reach 3.
- **Why 60 s:** the measured error names a per-minute quota. A daily-quota 429 would re-pause every minute, which costs one wasted call per key per minute. This is marked `ponytail:` in the code.
- **Accepted edge:** the streak counts all failures, so a 503 followed by two 429s also pauses the key. A 503 on its own never reaches this code, which fits the rule that a 503 is per model and not per key.
- **User-visible effect when all 11 keys are paused at once:** the claim returns `all_keys_cooling`, and the chat shows the existing 429 sentence "The AI quota is used up for now. Try again later." This is the same contract as today; no new shape.

## Fix 2: first-chunk timeout (streaming only)

- `client.ts` gains a new option, `GenerateGeminiOptions.firstChunkTimeoutMs`. It is ignored unless `onText` is set, and an absent value gives exactly the old behaviour.
- For each attempt:
  - An `AbortController` timer is combined with the total timeout through `AbortSignal.any`.
  - The timer is disarmed in three cases: on the first body bytes (`readGeminiStream` `onFirstBytes`), on any non-stream or error response (so a real 429/503 body read is never turned into a fake timeout), and in `finally`.
  - When it fires, the attempt returns status 0 with `statusText "timeout: no first chunk after Nms"`. The usage log buckets that as `timeout`, the loop treats it as transient and moves to the next key, and the stream sends the existing "No answer yet - trying again..." status.
- **Contract:** there is no new response shape, no new op kind and no new reason.
- `resume-assist/assist.ts` passes `firstChunkTimeoutMs: 8_000`. `timeoutMs` stays at 15 s and thinking stays "low".
  - **The 8 s value is a guess and needs tuning from live logs.** After deploy, measure it: count `gemini_usage` rows where agent = `resume-assist` and outcome = `timeout`. If healthy chats get cut, raise it.
- The fast path was not built (Teja's ruling).
