# 2026-11-12 17:10 IST: peer 1 (30) fixes skill adds on older rows being refused with "master changed"

**Status:** done and gated. **Not committed.** This is a web-only change; Vercel ships it on push. No DB, function or migration change.

## Which side refused: the web
- The refusal came from `apps/web/src/features/approval/attestSkill.ts`, the `CHANGED_MASTER` path in `rebuildAt`.
- Every chat `add_skill` goes through `attestSkill`. That always targeted the **latest** master and re-pinned the row to it.
- After v45 and v47, rebuilding an older row at the latest version changed other lines, such as dropped twins and LLM Applications. The proof failed, so every add was refused.

## The fix
- New `addAtPin()` in `attestSkill.ts` adds the skill against the row's **pinned** master (`AttestArgs.pinnedMaster`, a required field). The page passes it from `source.master` in `ApprovalQueuePage.tsx`.
- **When it runs:** when the pinned master already holds the skill. It matches by the tailor's rule (`addableSkillFor`) or by name (`masterSkillNamed`), checked right after the duplicate-on-resume check.
- **What changes:**
  - Nothing is written to the master.
  - There is no `repin`, so `master_version` and `tailor_refs` are untouched.
  - The update writes `tailored_profile` only: the old skills plus the one added.
- **What still applies:**
  - The one-full-line wrap guard from c01372e, with the "all" override.
  - The one-page fit.
  - The optimistic stamp.
- The event is `resume_add_skill`, because the pin did not move.
- A skill the pinned master lacks still takes the old attest path: a new master version and a re-pin. On a row that predates v47, that path can still refuse with `CHANGED_MASTER`.
