## Counter-reset SQL — for the ORCH to run (live write)

Live, read-only, 2026-11-21 ~10:35 IST: 64 enabled Workday boards, **59 at `consecutive_failures >= 5`**,
max 32. Most of those counts came from robots.txt 429s that D1 now skips without counting. Without a
reset, D10 rests all 59 for 24 h after this ships.

**Order:** run only AFTER the commit is on `origin/main` and no `scout.yml` run is in progress
(`gh run list --workflow=scout.yml --limit 3`). Old code running after the reset re-inflates the counts.

```sql
-- PREVIEW (read-only): the rows the UPDATE will touch
select id, board_token, consecutive_failures, last_polled_at
from public.company_watchlist
where ats_provider = 'workday' and enabled and consecutive_failures > 0
order by consecutive_failures desc;
```

```sql
-- RESET: Workday failure streaks were inflated by robots.txt 429s (D1); D1 now skips those uncounted,
-- so a fresh streak measures real page failures only. last_polled_at is left alone.
update public.company_watchlist
set consecutive_failures = 0
where ats_provider = 'workday' and enabled and consecutive_failures > 0;
-- expect the row count to equal the preview's
```

Caveat: if Cloudflare also blocks the job-list POSTs from GitHub-runner IPs (the open egress question),
the counts will climb back via real page failures and D10 will rest those boards again. That is the
correct signal, not a regression.
