## Headers copied exactly from the scout (this matters)

The scout sends **two different User-Agents**:

| Request | Headers | Source |
|---|---|---|
| robots.txt GET | `user-agent: applyy-scout` (bare product token), `accept: text/plain, */*;q=0.1` | `packages/master-robots/src/fetch.ts:86-95` |
| jobs POST | `User-Agent: applyy-scout/1.0 (+https://github.com/MallamTeja/applyyy)`, `Accept: application/json`, `Content-Type: application/json` | `worker/src/scout/board-pages.ts:26-30, :204` |

The POST body is `{"appliedFacets":{},"limit":1,"offset":0,"searchText":""}`. The key order matches the scout's own body (`workday.ts:263-272`).

A robots-only block could therefore be UA-shaped, not IP-shaped. The probe can tell those apart only by comparing the runner with home.

## Guards added beyond the brief

- **Honor robots.** If robots.txt is a 200 that disallows any prefix of `/wday/cxs/`, the script skips that tenant's POST (`SKIPPED_ROBOTS_DISALLOW`).
  - The check is group-agnostic, so it is stricter than the scout's and fails closed.
  - Inline check: 7/7 cases pass (`/`, `/wday/`, empty, an unrelated path, a deeper path, a commented rule, a wildcard).
  - No separate test file. The logic is one function, and the script runs `main()` on import.
- **Outage.** A body containing `ERR_TENANT_OUTAGE` is flagged as `outage`. The POST is skipped (`SKIPPED_OUTAGE`), and the run ends with `verdict: INCONCLUSIVE`.
- **Flag for the orch:** after a robots **429** the script still sends one limit-1 POST. That is the whole experiment, but it departs from the scout, which never POSTs when robots.txt can't be read. Teja's "Honor robots" ruling is about Disallow, and a 429 is not a Disallow. Even so, this is the orch's call to own.
