## Behaviour

When the DB refuses `approved → applying` with errcode **23505** (a second copy of a posting this user already has at applying | blocked_needs_human | applied):
- **Gateway** (`worker/src/supabase-gateway.ts` `advanceStatus`): supabase-js returns `{ error: { code: '23505' } }` and does not throw. The gateway maps that to a typed `DuplicatePostingAppliedError`, but **only** when `to === 'applying'` AND the code is exactly `'23505'`.
  - A 23505 on any other move, or any other code on this move, keeps today's plain throw (`unwrap`).
- **Bot applier** (`worker/src/apply-one.ts`, the move at the non-idempotent window): it catches only that type, then:
  - releases the lease with the reason `duplicate posting already applied: application <id> refused entering applying (<db message>); row left approved`;
  - returns the new outcome `{ kind: 'duplicate_already_applied', reason }`.
  - Nothing is clicked, because the move comes before `page.submit()`. No `failed` write, no retry.
- **Claim loop** (`worker/src/claim-loop.ts`):
  - a new `duplicateAlreadyApplied` tally and `RunSummary.duplicateAlreadyApplied`;
  - a named run-log line `[applyy] <reason>`;
  - **no breaker trip** (it is not `submit_outcome_unknown`, a captcha, or a throw);
  - the next row proceeds.
  - The released row comes straight back on the next claim (it is the oldest approved row). The existing re-claim guard holds it and releases it once at run end with "already processed earlier in this run", the same path dry-run rows take, so it is never attempted twice in one run.
- **Assisted path** (`worker/src/assist/assisted-submit.ts`): `log("already applied to this posting (<company> <title>), row left approved")` and `return { kind: 'duplicate_already_applied' }`, a value, not a stack trace.
  - `advanced` stays false, so the existing `finally` releases the lease.
- **New file** `worker/src/duplicate-posting.ts`: the error class plus `DUPLICATE_POSTING_ERRCODE`. It is its own module because the gateway already imports apply-one's types, so apply-one importing from the gateway would load the Supabase layer into the applier at runtime.
- Workflow readers of RunSummary: **none**. A grep of `.github/workflows/` for `atsUnsupported|robotsRefused|outcomeUnknown|stopKind|RunSummary` returns nothing, so no step needs to be made lenient.
